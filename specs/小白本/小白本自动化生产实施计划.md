# 小白本自动化生产实施计划

> 依据文档：`specs/小白本/小白本自动化生产流程.md`
> 适用范围：小白本生产链路自动化建设
> 文档目标：将现有流程节点、流程图和分期信息，拆解为可执行、可排期、可验收的实施方案

---

## 1. 背景说明

当前 [小白本自动化生产流程.md](./小白本自动化生产流程.md) 已明确小白本生产自动化的主链路：

1. 接单（已完成）
2. 翻译（已完成）
3. 打印指令（一期）
4. 自动化打印（一期）
5. 快递单（二期）
6. 打包（二期）

结合流程图可进一步理解为：

- 上游由 `agent接单平台` 持续推送订单。
- 订单先进入 `订单池（未翻译）`，再通过 `AI自动化` 转入 `订单池（已翻译）`。
- 已翻译订单再按渠道或来源分流至 `携程订单 / SIXT订单 / KLook订单 / SIDL订单 / 其他订单`。
- 其中核心自动化主线是：`携程订单 -> 自动化生产 -> 小白本 -> 匹配 -> 快递单 -> 打包发货`。
- 图中还额外提出了一个后续议题：`NFC如何自动化写入，识别NFC后识别快递单`，说明后续可能继续演进到更深的生产末端自动化。

这意味着当前要做的，不只是“把 6 个节点写成说明”，而是要把“订单进入系统后，如何变成可自动执行的生产任务”定义清楚，并把打印、快递单、打包三个后续节点拆成真正能落地的能力建设项。

---

## 2. 实施目标

### 2.1 总体目标

- 建立小白本从接单、翻译、打印到发货的标准化自动化主链路。
- 让系统从“人工切换工具执行”升级为“系统生成任务、系统驱动执行、人工处理异常”。
- 降低人工判断、重复点击、重复录入与漏操作风险。
- 让每个关键节点具备状态追踪、异常识别、失败回退和人工接管能力。
- 为未来继续扩展到 NFC、批量生产、更多渠道接入预留统一能力底座。

### 2.2 分期目标

| 阶段 | 目标 | 核心结果 |
| --- | --- | --- |
| 已完成 | 打通接单、翻译 | 订单能够进入系统并形成可用的翻译产出 |
| 一期 | 打通打印闭环 | 系统可基于订单自动生成打印任务并驱动自动化打印 |
| 二期 | 打通发货协同闭环 | 系统可联动快递单、打包动作和发货状态回写 |
| 后续演进 | 探索物理载体自动识别 | 评估 NFC 写入与识别后自动匹配快递单的可行性 |

### 2.3 成功定义

如果本项目实施成功，应达到以下业务结果：

- 小白本订单不再依赖人工逐单切换工具完成打印准备。
- 打印前的关键数据、模板、份数、通道规则均由系统自动校验。
- 一期即可实现生产主链路闭环，人工只处理异常单、失败单和人工通道订单。
- 二期后发货末端不再割裂，快递单、打包、发货形成连续流程。

## 3. 流程理解与实施边界

### 3.1 对原流程图的实施解读

原流程图中虽然只画了核心节点，但落地时可以拆解为以下 4 层：

| 层级 | 含义 | 本次是否纳入 |
| --- | --- | --- |
| 上游接入层 | agent 接单平台推单、渠道订单识别、订单池落库 | 已完成，需补核 |
| 内容生产层 | 翻译、模板匹配、打印指令生成、打印执行 | 一期重点 |
| 履约协同层 | 快递单匹配、面单生成、打包确认、发货回写 | 二期重点 |
| 设备扩展层 | NFC、扫码识别、物理载体自动关联 | 本次仅预留，不纳入当前交付 |

### 3.2 当前流程的关键断点

按照现有信息，当前最可能存在的断点包括：

- 订单进入系统后，虽然已经完成翻译，但未形成标准化打印任务。
- 已翻译订单虽有渠道分流，但“不同渠道订单是否走统一生产动作”尚未明确固化。
- 小白本与快递单之间的“匹配”规则还未被系统化定义。
- 打包可能仍是线下经验动作，缺少系统确认与状态约束。

### 3.3 本次实施边界

本计划聚焦以下内容：

- 小白本自动化生产的主链路实施方案
- 已翻译订单进入生产阶段后的任务拆解
- 一期打印任务、打印执行与异常处理机制
- 二期快递单、打包、发货协同机制
- 上线策略、回滚策略、验收标准与风险控制

本计划暂不纳入以下内容：

- 账号体系重构
- 支付链路改造
- 非小白本产品的全量流程统一
- 财务结算、对账、发票能力
- NFC 自动写入与硬件联动实施

## 4. 总体实施策略

建议采用“先定义任务，再驱动执行；先固化一期主链路，再延展二期协同链路”的方式推进。

### 4.1 推进原则

- 先保证订单到小白本打印可闭环，再继续推进物流与打包。
- 每个阶段必须有明确输入、处理规则、输出结果和异常处理机制。
- 自动化链路必须保留人工兜底入口，避免自动化失败导致履约中断。
- 渠道差异只放在接单与规则层，生产动作尽量统一。
- 一期优先做“可稳定运行”，二期再做“协同效率最大化”。

### 4.2 分阶段策略

| 阶段 | 实施重点 | 目标原则 |
| --- | --- | --- |
| 阶段A | 巩固接单、翻译输出 | 确保上游输入稳定、翻译结果可用于生产 |
| 阶段B | 建设生产任务模型 | 让系统可以把订单转成可执行的生产任务 |
| 阶段C | 建设打印指令能力 | 让系统具备生成标准化打印指令的能力 |
| 阶段D | 建设自动化打印能力 | 让打印动作从人工操作升级为系统驱动 |
| 阶段E | 建设快递单协同能力 | 让文档生产结果与物流面单建立自动关联 |
| 阶段F | 建设打包与发货能力 | 让生产末端动作可校验、可确认、可回写 |

### 4.3 推荐产品策略

- 将“订单”与“生产任务”拆开管理。
- 将“小白本打印任务”和“快递单打印任务”拆成两个子任务。
- 将“自动通道”和“人工通道”作为系统派生能力，而不是人工判断。
- 将“匹配”节点定义为一套明确规则，而不是线下口径。

## 5. 目标流程（TO-BE）

建议将目标流程明确为以下链路：

```text
agent接单平台
-> 订单池（未翻译）
-> 自动翻译
-> 订单池（已翻译）
-> 渠道归类 / 生产规则识别
-> 生成小白本生产任务
-> 模板匹配 / 数据校验
-> 生成打印指令
-> 自动化打印小白本
-> 匹配快递单
-> 打印快递单
-> 打包确认
-> 发货回写
```

### 5.1 关键设计思想

- 订单是业务对象，生产任务是执行对象。
- 渠道分流影响规则，但不应打散主生产流程。
- 任何自动化动作前都要先经过系统校验。
- 快递单与打包不应只存在于线下动作里，必须进入系统状态管理。

### 5.2 通道设计建议

结合现有生产端相关 PRD，建议延续以下规则：

- `copy_count = 1` 默认进入自动通道。
- `copy_count = 2` 或 `3` 默认进入人工通道。
- 自动通道若任一准入条件失败，则自动降级为人工通道。

这类规则即使未全部写在原始流程文档中，也应作为实施计划里的明确落地规则，否则后续开发无法判断什么订单能真正进入自动化生产。

## 6. 核心对象与状态设计

### 6.1 核心对象建议

| 对象 | 说明 | 作用 |
| --- | --- | --- |
| 订单 | 上游推送的小白本业务单据 | 业务源数据 |
| 翻译任务 | 负责翻译执行和翻译结果回填 | 内容生产前置任务 |
| 生产任务 | 负责承接小白本制作主流程 | 主执行载体 |
| 小白本打印任务 | 负责文档打印 | 一期核心任务 |
| 快递单任务 | 负责面单生成与打印 | 二期核心任务 |
| 打包任务 | 负责物料校验与打包确认 | 二期末端任务 |

### 6.2 建议状态口径

#### 订单状态

- 已接单
- 翻译中
- 待人工校对
- 待生产
- 生产中
- 待发货
- 已发货
- 异常中

#### 小白本打印任务状态

- 待生成
- 待校验
- 待打印
- 打印中
- 打印成功
- 打印失败
- 已补打

#### 快递单任务状态

- 待匹配
- 待生成
- 待打印
- 打印成功
- 打印失败

#### 打包状态

- 待打包
- 打包中
- 已打包
- 打包异常

### 6.3 状态设计原则

- 订单主状态用于体现业务进度。
- 子任务状态用于体现执行进度。
- 子任务失败不应直接污染订单主状态，但应阻断后续自动流转。
- 所有失败状态都应支持“记录原因 + 重新执行 + 人工接管”。

## 7. 分阶段实施计划

### 7.1 阶段A：接单与翻译能力巩固（已完成，建议补核）

虽然该阶段标记为已完成，但建议在一期正式启动前做一次补核，确保打印链路不会因上游口径问题返工。

#### 阶段目标

- 确认接单字段完整，可支撑模板回填、打印和快递单生成。
- 确认翻译结果结构稳定，可直接作为生产输入。
- 确认渠道字段可被稳定识别，用于后续分流与规则匹配。
- 明确异常订单如何进入人工处理。

#### 建议补核项

| 补核项 | 说明 | 输出物 |
| --- | --- | --- |
| 接单字段检查 | 检查姓名、证件信息、语言、产品类型、份数、地址、渠道来源等字段完整性 | 字段清单 |
| 翻译结果检查 | 检查翻译结果是否包含结构化字段、置信度、人工校验标识 | 翻译输出规范 |
| 渠道识别检查 | 检查携程、SIXT、KLook、SIDL、其他订单的识别条件 | 渠道识别规则 |
| 异常回退检查 | 检查翻译失败、字段缺失、模板不匹配时如何处理 | 异常处理说明 |

#### 验收口径

- 打印所需核心字段可稳定获取。
- 渠道来源可稳定识别。
- 异常订单可以被识别并转入人工处理，不阻塞主流程。

---

### 7.2 阶段B：生产任务模型（一期）

这一阶段是建议新增的，因为要真正落地后续流程，单靠“订单状态”不够，需要先把生产任务抽象出来。

#### 阶段目标

- 让已翻译订单可以被系统自动转换为标准生产任务。
- 让后续打印、快递单、打包都围绕统一任务对象执行。

#### 建设内容

| 模块 | 建设内容 | 说明 |
| --- | --- | --- |
| 任务创建 | 已翻译订单自动生成生产任务 | 生产任务成为后续动作入口 |
| 通道判定 | 自动判断自动通道 / 人工通道 | 减少人工分单 |
| 渠道标识 | 在任务层带出渠道信息 | 便于差异化规则处理 |
| 优先级计算 | 根据办理类型、加急属性计算优先级 | 便于排队与执行 |
| 异常挂起 | 识别不满足生产条件的订单并挂起 | 避免错误流转 |

#### 建议字段

| 字段 | 说明 |
| --- | --- |
| `production_task_id` | 生产任务唯一标识 |
| `order_id` | 关联订单 |
| `channel_code` | 渠道来源 |
| `copy_count` | 本数 |
| `route_type` | 自动通道 / 人工通道 |
| `priority_level` | 普通 / 优先 / 加急 |
| `production_status` | 待生产 / 生产中 / 已完成 / 异常 |
| `exception_reason` | 异常原因 |

#### 交付物

- 生产任务模型定义
- 通道判定规则文档
- 任务创建时机说明
- 异常挂起规则

#### 验收标准

- 已翻译订单可自动生成生产任务。
- 生产任务能自动判断进入自动通道还是人工通道。
- 异常任务不会直接进入打印阶段。

---

### 7.3 阶段C：打印指令（一期）

#### 阶段目标

把“打印”从人工动作抽象为系统内可管理的标准任务，为自动化打印做准备。

#### 建设内容

| 模块 | 建设内容 | 说明 |
| --- | --- | --- |
| 打印任务模型 | 定义打印任务、打印份数、模板版本、打印状态 | 形成统一任务口径 |
| 打印指令生成 | 根据订单、翻译结果和模板规则自动生成打印指令 | 减少人工组装 |
| 模板映射规则 | 建立产品、语言、国家、渠道与模板之间的映射关系 | 避免打错模板 |
| 打印前校验 | 校验关键字段、模板完整性、份数、通道、准驾车型等 | 降低废单风险 |
| 预览确认能力 | 支持在打印前查看渲染结果 | 降低格式问题 |
| 状态流转 | 待生成、待校验、待打印、打印中、成功、失败 | 便于追踪 |

#### 对“打印指令”的建议定义

打印指令至少应包含：

- 打印对象：小白本文档 / 快递面单
- 关联订单与生产任务
- 模板编号与模板版本
- 打印份数
- 打印设备或打印服务目标
- 执行顺序
- 重试次数
- 生成时间与触发来源

#### 交付物

- 打印任务字段定义
- 打印指令生成规则文档
- 模板映射配置表
- 打印前校验规则
- 打印状态流转说明

#### 关键依赖

- 翻译结果结构稳定
- 模板版本已确定
- 渠道到模板的匹配口径明确
- 打印设备接入方式已明确

#### 风险点与应对

| 风险 | 影响 | 应对措施 |
| --- | --- | --- |
| 上游字段缺失 | 无法生成打印指令 | 增加打印前校验并阻断流转 |
| 模板映射错误 | 打印内容错误 | 模板版本化管理，配置双人确认 |
| 渠道差异未收敛 | 指令规则复杂失控 | 将渠道差异限制在配置层 |
| 状态口径不清 | 无法定位异常 | 统一打印任务状态枚举 |

#### 验收标准

- 系统可基于订单自动生成打印指令。
- 打印前能识别字段缺失、模板缺失、通道不满足等异常。
- 每个订单的打印任务状态可查询、可追踪、可重试。

---

### 7.4 阶段D：自动化打印（一期）

#### 阶段目标

在打印指令标准化基础上，实现系统直接驱动打印动作，形成一期核心闭环。

#### 建设内容

| 模块 | 建设内容 | 说明 |
| --- | --- | --- |
| 打印执行器接入 | 对接本地打印程序、打印服务或打印机控制中间层 | 实现自动下发 |
| 队列调度 | 控制任务排队、并发和重试 | 避免设备冲突 |
| 串行执行机制 | 先按小白本主文档要求执行打印动作 | 保证顺序可控 |
| 结果回写 | 成功、失败、重试结果回写系统 | 支撑追踪与补打 |
| 补打机制 | 支持失败补打、人工补打和重新渲染 | 降低中断影响 |
| 日志记录 | 记录设备、时间、操作者、失败原因 | 便于排查 |

#### 推荐实施方式

- 优先采用“系统生成任务 + 打印服务消费任务 + 回写结果”的模式。
- 将模板渲染与打印执行分层，避免设备问题与模板问题相互混淆。
- 保留人工触发补打入口，作为一期兜底能力。

#### 建议异常分类

| 异常类型 | 示例 | 处理方式 |
| --- | --- | --- |
| 数据异常 | 字段缺失、模板缺失 | 阻断并转人工 |
| 渲染异常 | HTML 转打印稿失败 | 允许重渲染 |
| 设备异常 | 打印机离线、卡纸、无响应 | 重试或换设备 |
| 输出异常 | 打印内容错位、页数不对 | 人工复核并补打 |

#### 交付物

- 自动化打印执行方案
- 打印服务对接说明
- 打印日志字段定义
- 补打操作说明
- 异常分类与处理清单

#### 验收标准

- 打印任务可自动执行，无需人工逐单操作。
- 打印成功与失败结果可回写系统。
- 打印失败后可执行补打，不影响其他订单继续处理。
- 异常任务可回退到人工通道，不造成整批阻塞。

---

### 7.5 阶段E：快递单（二期）

#### 阶段目标

将快递单能力纳入生产链路，使小白本生产结果与物流信息形成系统内联动。

#### 对流程图中“匹配”的建议解读

流程图里 `小白本 -> 匹配 -> 快递单` 中的“匹配”，建议定义为以下规则集合：

- 小白本生产任务与订单收货信息匹配
- 小白本生产任务与物流产品类型匹配
- 小白本生产任务与快递单模板匹配
- 小白本生产结果与待发货物料数量匹配

如果不把“匹配”节点定义清楚，二期会很容易退化回线下人工判断。

#### 建设内容

| 模块 | 建设内容 | 说明 |
| --- | --- | --- |
| 快递信息获取 | 获取收件人、电话、地址、物流方式、配送类型 | 作为面单输入 |
| 面单匹配规则 | 根据订单与生产结果匹配快递单能力 | 固化“匹配”逻辑 |
| 面单任务生成 | 为订单生成快递单打印任务 | 与文档打印关联 |
| 面单打印状态 | 记录待打印、成功、失败、补打状态 | 独立追踪 |
| 物流字段回写 | 回写快递公司、单号、面单打印时间 | 支撑发货管理 |
| 异常兜底 | 支持人工补录单号或改物流方式 | 避免系统卡死 |

#### 建议策略

- 快递单与小白本文档打印应拆分成两个子任务，但可在操作上合并成一个生产动作。
- 二期先实现“面单生成 + 打印 + 单号回写”，物流轨迹同步可后续扩展。
- 若未来要求“一键打印”，则顺序应固定为“先快递单，后小白本”或“先小白本，后快递单”，需要在产品层统一。若沿用生产端既有口径，则建议固定为“先快递单，后文档”。

#### 交付物

- 快递单字段清单
- 面单匹配规则说明
- 面单任务模型
- 快递打印状态说明
- 物流回写规则

#### 验收标准

- 系统可生成并打印快递单。
- 快递单结果与订单、小白本生产任务建立关联。
- 物流单号、快递公司等信息可回写系统。
- 面单失败不会导致订单无状态可追踪。

---

### 7.6 阶段F：打包（二期）

#### 阶段目标

把打包动作从线下经验操作升级为系统管理节点，为最终发货闭环提供支撑。

#### 建设内容

| 模块 | 建设内容 | 说明 |
| --- | --- | --- |
| 打包节点定义 | 明确待打包、打包中、已打包、打包异常状态 | 建立标准节点 |
| 打包校验清单 | 校验小白本、快递单、份数、附件、配套物料是否齐备 | 降低漏件风险 |
| 操作确认 | 支持打包完成确认及责任记录 | 便于追责与复盘 |
| 发货前校验 | 打包完成后才允许进入发货 | 形成顺序控制 |
| 异常记录 | 缺件、破损、需补印、信息不一致等情况记录 | 支撑异常处理 |
| 发货回写 | 打包完成并发货后回写订单状态 | 完成业务闭环 |

#### 建议打包校验清单

- 小白本实物数量是否与 `copy_count` 一致
- 快递单是否已打印且信息一致
- 收件人姓名、电话、地址是否一致
- 是否存在加急标识或特殊发货要求
- 是否存在补印、重打或异常改单情况

#### 交付物

- 打包节点状态定义
- 打包校验清单
- 打包完成确认流程
- 打包异常处理说明
- 发货回写规则

#### 验收标准

- 打包前可校验关键物料是否齐全。
- 打包完成后系统可记录状态、时间和责任人。
- 未完成打包的订单不可进入发货完成状态。
- 发货回写后，订单主状态与履约状态保持一致。

## 8. 一期与二期的拆分建议

### 8.1 一期范围

- 接单、翻译结果补核
- 生产任务模型
- 自动 / 人工通道规则
- 打印任务模型
- 打印指令生成
- 模板匹配与打印前校验
- 自动化打印执行
- 打印异常处理与补打

### 8.2 二期范围

- 面单匹配规则
- 快递单任务生成与打印
- 物流字段回写
- 打包状态与打包校验清单
- 发货回写

### 8.3 不建议一期硬塞进去的内容

- NFC 自动写入
- 物流轨迹全链路同步
- 大规模多设备调度优化
- 所有渠道的深度个性化规则

## 9. 上线策略建议

### 9.1 灰度策略

建议按以下顺序灰度：

1. 仅灰度单一渠道，如携程订单
2. 仅灰度 `copy_count = 1` 的自动通道订单
3. 仅灰度固定模板版本
4. 打印成功率稳定后再扩大渠道和订单量

### 9.2 开关策略

建议保留以下开关能力：

- 自动翻译开关
- 自动通道开关
- 自动打印开关
- 面单自动生成开关
- 打包校验强制开关

### 9.3 回滚策略

一旦出现异常，至少应支持：

- 自动通道退回人工通道
- 自动打印退回人工打印
- 快递单自动生成退回人工面单处理
- 打包确认退回人工线下执行后再补录状态

## 13. 风险总表

| 风险 | 所在阶段 | 影响 | 建议处理 |
| --- | --- | --- | --- |
| 上游字段口径变化 | 阶段A/B/C | 打印指令生成失败 | 冻结一期字段口径并设变更流程 |
| 渠道规则不一致 | 阶段A/B | 同一订单无法稳定进入生产 | 将差异沉淀为配置规则 |
| 模板频繁调整 | 阶段C/D | 打印稳定性下降 | 模板版本管理，灰度发布 |
| 打印设备不稳定 | 阶段D | 自动化成功率低 | 先限定设备，保留人工补打 |
| 面单匹配规则不清 | 阶段E | 快递单无法自动联动 | 提前定义匹配口径并联调验证 |
| 地址质量不高 | 阶段E | 面单错误、错发 | 增加地址校验和人工确认 |
| 打包执行不一致 | 阶段F | 发货质量不可控 | 建立 SOP、培训与责任记录 |
| 开关与回滚缺失 | 全阶段 | 上线风险不可控 | 所有自动化关键节点保留降级开关 |

### 14.3 最终验收口径

#### 一期验收

- 接单、翻译、生产任务、打印指令、自动化打印形成闭环。
- 系统可自动生成打印任务并执行打印。
- 自动通道与人工通道规则可被稳定执行。
- 打印结果、失败原因、补打记录均可追踪。

#### 二期验收

- 快递单与小白本生产任务建立关联。
- 打包节点纳入系统流程管理。
- 从接单到翻译、生产、面单、打包、发货形成完整履约链路。

## 15. 后续演进建议

流程图中提到“`NFC如何自动化写入，识别NFC后识别快递单`”，建议作为后续独立议题处理：

- 先在当前项目中预留订单、物理件、快递单三者的唯一关联标识。
- 等一期、二期稳定后，再单独评估 NFC 写入硬件、读取流程和识别准确率。
- 不建议在本期把 NFC 与主流程强绑定，否则会显著增加复杂度与上线风险。

---

## 16. 建议结论

建议将小白本自动化生产明确拆为“两期主建设 + 一期后灰度 + 后续能力演进”的推进方式：

- 一期聚焦“生产主链路自动化”，核心是生产任务、打印指令和自动化打印闭环。
- 二期聚焦“履约末端协同”，核心是快递单、打包和发货回写闭环。
- NFC 等设备联动能力放在后续独立议题中评估，不挤占当前主流程建设资源。

这样既能尽快解决当前最核心的生产效率问题，也能把流程图里的后续协同能力逐步落到系统里，整体风险更可控，实施节奏也更清晰。
